# REF-001: Rocky Engineering Handbook

## Authority and lifecycle

The [charter](../charters/RKY-000.md) governs purpose; PRDs govern outcomes; accepted ADRs govern
architecture; an EPKG governs one bounded delivery. When artifacts conflict, that order prevails,
then the more recently accepted artifact at the same level. A conflict must be resolved in the
canonical artifact, never patched with a second definition.

Artifact statuses are `draft`, `proposed`, `accepted`, `superseded`, and `rejected`. Accepted ADRs
are not edited to change a decision: create a successor and add reciprocal supersession links.
Other accepted artifacts receive a semantic `version` change and an updated date when normative
meaning changes. IDs are permanent and zero-padded within their series.

## Delivery lifecycle

1. **Frame:** confirm alignment with RKY-000 and create or reference an accepted PRD.
2. **Decide:** record consequential, cross-cutting, or difficult-to-reverse choices as ADRs.
3. **Package:** allocate an EPKG ID and derive its SPEC from the governing artifacts.
4. **Execute:** use PROMPT as optional provider-neutral guidance; code and docs remain authoritative.
5. **Verify:** run TESTS, record results, and complete REVIEW against the SPEC.
6. **Accept:** a maintainer reviews the diff and evidence, then merges through normal repository controls.

Use the [glossary](../glossary.md) for artifact meanings and the
[templates](../../templates/README.md) for required structure.

## Engineering rules

- Scope each change to one coherent outcome and link its EPKG in the change description.
- Read root and nearest scoped instructions before editing. Never rely on inaccessible conversations.
- Do not implement speculative domain abstractions. Prefer the smallest reversible design.
- Put shared terminology only in the glossary and shared policy only in this handbook.
- Keep source, tests, documentation, and artifact evidence synchronized.
- No import-time side effects, secrets, generated caches, or vendor-specific agent configuration.
- Review the final diff for unrelated edits, repetition, contradictions, placeholders, and stale links.

## Engineering Domains

An Engineering Domain is a bounded model of governed engineering concepts, policies, and behavior.
Repository artifacts remain the source of product and architecture authority; domain implementation
does not replace PRDs, ADRs, EPKGs, or review evidence. Domain policy remains independent from
persistence, infrastructure, external providers, delivery tools, and AI providers. Public contracts
must be minimal, explicit, justified by consumers, and must not expose internals. Intelligence and
automation may consume domain contracts but must not own domain policy.

New domains require:

1. alignment with RKY-000;
2. an accepted PRD;
3. an accepted ADR only when the decision is consequential or cross-cutting;
4. a dedicated EPKG; and
5. review and validation evidence before acceptance.

Domain-specific lifecycle states, aggregates, value objects, ports, and use cases belong in the
domain's EPKG rather than in this handbook.

## Quality gates

The repository root exposes the authoritative commands: `make lint`, `make type-check`,
`make test`, and `make links`; `make check` runs all four. A change may be accepted only when each
gate passes, or when a REVIEW names the environmental limitation, risk, owner, and follow-up. Tests
must cover behavior rather than implementation details. Documentation-only work still runs every
gate and validates relative links.

## Review and security

Reviewers verify traceability, acceptance criteria, architecture compliance, tests, documentation,
and absence of secrets or unnecessary dependencies. Agent output is untrusted contribution: inspect
the diff and execute validations. Maintainers retain responsibility for licensing, privacy, threat
modeling, and release approval.
