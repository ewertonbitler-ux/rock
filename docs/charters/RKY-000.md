# RKY-000: Rocky Product Charter

## Mission

Make software delivery explainable and repeatable by keeping product intent, architecture,
execution guidance, and verification evidence in the repository that they govern.

## Problem

Engineering teams lose decisions across tickets, chat, personal notes, and tool-specific agent
configuration. Implementation then outruns intent: reviewers cannot identify the governing
requirement, automation receives incomplete context, and future maintainers must reverse-engineer
trade-offs. Rocky establishes a small, connected artifact system that remains useful without any
particular project-management or AI provider.

## Principles

1. **Architecture first.** Establish constraints before choosing implementation details.
2. **Repository as knowledge.** Version canonical context with the affected system.
3. **Traceability over ceremony.** Every artifact must clarify a decision or provide evidence.
4. **Provider neutrality.** Guidance describes roles and contracts, not vendor integrations.
5. **Human accountability.** Agents may assist; maintainers own acceptance and consequential decisions.
6. **Progressive detail.** Charter, PRD, ADR, and EPKG artifacts narrow intent without duplicating it.

## Boundaries

Rocky defines engineering documentation, navigation, templates, validation, and a minimal Python
bootstrap. It does not define future product domain models, run an autonomous delivery service,
replace issue tracking, or prescribe an AI provider. Domain capabilities require their own PRD and
EPKG.

## Stakeholders and success

Maintainers need durable governance; contributors need an unambiguous path from request to proof;
reviewers need concise acceptance evidence; automation needs bounded context. Rocky succeeds when:

- every implementation package identifies its governing PRD and applicable ADRs;
- required local checks are reproducible from the repository root;
- all repository-local documentation links resolve;
- accepted decisions have explicit consequences and supersession paths; and
- a new contributor can locate product intent, workflow, and current package context from the root.

The concrete first-release outcomes are defined in [PRD-001](../prd/PRD-001.md).
